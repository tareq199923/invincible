See a rate limit not stop you

One stable endpoint. When one of your provider credentials hits its limit, Invincible cools it down and retries the next — the session keeps going.

x-invincible-provider: provider-b · x-invincible-attempts: 2

Example: a coding agent's request hits a rate limit on Provider A. Invincible cools that credential down and retries Provider B, which answers. The session continues with no action from the user.

What's inside

Four parts. Use one or all of them.

Use the gateway, memory, and continuity from the clients you already have. Add the paired agent only when you need actions on a machine. Your provider credentials and saved state remain attached to your account.

Gateway

OpenAI Chat Completions, Anthropic Messages, and OpenAI Responses client APIs route through your own OpenAI-compatible provider credentials. Choose auto, pinned, or chain routing; eligible rate limits, server errors, and network failures can move to your next credential.

You'll need: your provider key. There is no shared provider pool.

Memory

Account- and project-scoped memories are stored in PostgreSQL. Retrieval is lexical, combining full-text relevance, recency, kind, and confidence within a bounded context budget. Ask the assistant to remember something to save it explicitly.

You'll need: an account. Semantic/vector search is not implemented.

Continuity

Keep task state distinct from memory. Versioned updates use optimistic checks; immutable checkpoints preserve important states, and tracked work can receive a snapshot before provider failover.

You'll need: a chat client. State belongs to your account.

Tools + Agent

Nineteen OAuth-protected MCP tools cover files, shell, search, directory and Git inspection, screenshots, memory, projects, and task continuity. Shell and file writes require single-use confirmation; machine jobs run on the paired agent when routing is enabled.

You'll need: an MCP client. Pair a machine for machine-side tools.

Connect a client

Wire it up in minutes

Connect an OpenAI-compatible Chat Completions provider with a public HTTPS URL. Its credentials stay encrypted on the service and never need to be sent to your AI client.

Chat — any OpenAI client
curl {{ base_url }}/v1/chat/completions \
  -H "Authorization: Bearer inv_…" \
  -H "X-Session-Id: my-conversation" \
  -d '{"messages": [{"role": "user",
    "content": "Hello!"}]}'

History under the session id is prepended upstream; the reply is persisted back. A 429 cools down and fails over — the client sees one stable endpoint.

Claude Code
export ANTHROPIC_BASE_URL="{{ base_url }}"
export ANTHROPIC_AUTH_TOKEN="inv_…"

No /v1 suffix — Claude appends it. Older Claude Code versions read ANTHROPIC_API_KEY instead; the gateway accepts both.
Windows PowerShell: $env:ANTHROPIC_BASE_URL="{{ base_url }}" $env:ANTHROPIC_AUTH_TOKEN="inv_…"

Codex — ~/.codex/config.toml
model_provider = "invincible"

[model_providers.invincible]
name = "Invincible"
base_url = "{{ base_url }}/v1"
env_key = "INVINCIBLE_API_KEY"
wire_api = "responses"

Add a model = "…" line with a model your connected provider serves, then set INVINCIBLE_API_KEY in the environment before launching Codex.

Tools — OAuth-enabled MCP client
{
  "mcpServers": {
    "invincible": {
      "url": "{{ base_url }}/mcp"
    }
  }
}

Approve the connector in the browser — OAuth 2.1 + PKCE mints the bearer token. In Claude.ai, add the connector by pasting {{ base_url }}/mcp into Settings → Connectors, then approve it in the browser. Destructive calls return a confirmation token first; nothing runs until you approve it.

Continuity and control

The pieces agent workflows need to keep working

Provider choice stays replaceable. Your account, projects, credentials, memory, and continuity state remain attached to Invincible.

Per-user BYOK failover

One stable endpoint for your agents. Choose auto, pinned, or chain routing; eligible rate limits, server errors, and network failures move to another of your credentials. Provider keys are encrypted at rest; account API keys are shown once and stored as hashes.

Versioned continuity

Pick up where you left off, even when a provider fails. Task state is versioned with optimistic checks, immutable checkpoints pin important states, and one pre-failover snapshot is captured before routing continues — only when task state exists.

Scoped lexical memory

Remember what matters across sessions and clients. PostgreSQL stores memories with layer, confidence, provenance, and project scope; retrieval uses full-text matching, recency, kind, and confidence under one bounded budget. Semantic/vector search is not implemented; say "remember this" to save explicitly.

Nineteen OAuth-protected MCP tools

Let capable clients act — carefully. File and shell operations, search, directory and Git inspection, screenshots, task state, checkpoints, memory, and projects are exposed over MCP. Shell execution and file writes require a single-use confirmation token.

Paired machine execution

Keep the security decisions server-side, run the work on your machine. When agent routing is enabled, machine jobs run on your paired computer over its outbound connection, inside a home-relative sandbox; confirmed actions keep their approval gate.

Usage and run history

See what your agents actually used. The dashboard aggregates attempts, failovers, and input/output token counts by day and provider/model, with provider-attempt history and continuity projections for tracked work.

FAQ

Frequently asked questions

Short answers with the same semantics the docs pin. Nothing here promises what the code does not do yet.

Do I need to run a server or a database?

No. Create an account on the hosted service and everything — providers, sessions, memory, task state — lives server-side. To reach a machine, install the CLI (pip install invincible-ai), pair it once (invincible harness setup), then keep it online (invincible harness connect). The same code also self-hosts on a laptop backed by PostgreSQL if you prefer to operate it yourself.

What happens when a provider rate-limits me?

Your agent retries one stable endpoint instead of dying on the first 429. A 429 or 5xx cools that credential down (30s, doubling to a 300s cap) and tries your next credential; a 401 or 403 disables it for the server's life and moves on. When every credential is exhausted the gateway answers 503.

Where do approved tool calls actually execute?

On a hosted deployment, on your paired machine; on a single-user self-host without agent routing, on the server host itself. Either way the server keeps every security decision (denylist, staging, single-use confirmation token, audit, per-user routing) and the agent only does the work inside a home-relative sandbox, with denylisted credential paths blocked. An offline agent answers immediately instead of hanging.

What does memory remember?

Scoped lexical memories in PostgreSQL — notes, facts, preferences, decisions — ranked by full-text relevance, recency, kind, and confidence under one bounded budget shared with the continuity brief. Say "remember this" to save explicitly, and manage or delete everything from the dashboard. Semantic or vector search is not built yet.

Which clients work with Invincible?

Any OpenAI-compatible chat client against /v1/chat/completions, Claude Code against /v1/messages via ANTHROPIC_BASE_URL, Codex against /v1/responses, and any MCP-compatible client against /mcp through the browser OAuth flow.

Is there a shared provider pool I can fall back to?

No. Every request routes only through your own connected provider credentials — encrypted at rest, never shared across accounts. With no credentials connected, chat answers 400 and tells you to connect one on the Providers page.

Can one account see another account's data?

No. Projects, credentials, sessions, runs, memories, continuity state, and MCP grants are all owner-scoped per account, verified by a closed multi-tenant audit — a foreign id reads exactly like an unknown one.

Bring a machine online only when you need it.

Chat, memory, and continuity need no pairing. When you want your MCP client to reach a computer, pair it once and keep it online — the agent connects outbound, and hosted users never run a server or database.
